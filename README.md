# tapsi-dr-task

صفحه برنامه‌ریزی نوبت چندخدمتی. کاربر دو یا سه خدمت، ترتیب دریافت و بازه حضور را می‌دهد. برنامه حداکثر سه برنامه معتبر را پیشنهاد می‌کند و ثبت یکی از آن‌ها را نشان می‌دهد.

روز ثابت `2026-10-03` و منطقه `Asia/Tehran` است. همه ساعت‌ها محلی و با دقت دقیقه هستند.

## دستورها

```bash
npm install
npm run dev
npm test
npm run build
npm run preview
```

`npm test` قواعد رتبه‌بندی، قرارداد Mock، پاسخ کهنه، تعارض ظرفیت و مسیر انتخاب تا ثبت را اجرا می‌کند. زمان بدترین حالت جستجو با برچسب `[bench]` چاپ می‌شود.

## داده و Mock

داده پایه در `sample-data.json` است. کنترل حالت‌ها پایین همین صفحه است، در بخش «کنترل Mock». با انتخاب هر حالت، شمارنده همان حالت از نو شروع می‌شود. «بازنشانی داده‌ها» ظرفیت، شمارنده ثبت و حالت را به پایه برمی‌گرداند و ورودی فرم را نگه می‌دارد.

| حالت | رفتار Mock | رفتار برنامه |
| --- | --- | --- |
| عادی | دریافت نوبت‌ها ۳۰۰ms، ثبت ۵۰۰ms | نمایش نتیجه و ثبت موفق |
| پاسخ خارج از ترتیب | جستجوی اول ۱۵۰۰ms، دوم ۲۰۰ms، بعدی ۳۰۰ms | نتیجه درخواست جدید می‌ماند و پاسخ دیررس آن را عوض نمی‌کند |
| خطای موقت دریافت | دریافت بعدی خطا، دریافت بعد از آن موفق | خطا و تلاش دوباره، بدون پاک شدن ورودی |
| تعارض ظرفیت | در لحظه ثبت، ظرفیت `c1` صفر می‌شود | خطای `SLOT_UNAVAILABLE`، بدون کاهش `a2` و `b1`، سپس محاسبه دوباره |

برای پاسخ خارج از ترتیب: حالت را انتخاب کنید، با ترتیب S1، S2، S3 و بازه `09:00–14:00` جستجو کنید، قبل از رسیدن پاسخ پایان را `10:50` بگذارید و دوباره جستجو کنید. نتیجه نهایی باید بدون برنامه بماند.

ثبت در Mock اتمیک است: شناسه‌ها باید موجود و متمایز باشند و فقط اگر همه ظرفیت داشته باشند، از هر کدام یکی کم می‌شود. هر پاسخ ظرفیت کپی مستقل است.

## خروجی نمونه

ترتیب S1، S2، S3 و بازه `09:00–14:00`:

| رتبه | نوبت‌ها | پایان | مجموع فاصله |
| --- | --- | --- | --- |
| ۱ | a2, b1, c1 | 10:55 | ۲۰ دقیقه |
| ۲ | a3, b3, c2 | 11:20 | ۳۰ دقیقه |
| ۳ | a2, b1, c2 | 11:20 | ۴۵ دقیقه |

`a2, b3, c2` هم پایان 11:20 و فاصله ۴۵ دقیقه دارد و به‌خاطر ترتیب شناسه بعد از ردیف سوم می‌ماند. با ظرفیت صفر `c1`، رتبه اول `a3, b3, c2` است. بازه `09:00–10:50` هیچ برنامه‌ای ندارد.

## معماری

وابستگی فقط به سمت داخل است.

- `src/domain` اعتبار برنامه، فاصله بین مرکزها و رتبه‌بندی. به React، DOM، شبکه و store وابسته نیست.
- `src/application` دریافت ظرفیت، جستجو و ثبت. شماره درخواست اینجاست تا پاسخ کهنه، حتی اگر Mock لغو نشود، نتیجه را عوض نکند.
- `src/infrastructure` داده ساختگی، تأخیر، خطای موقت و تعارض ظرفیت.
- `src/presentation` فرم، فازهای صفحه و Zustand.
- `src/composition/container.ts` پورت‌ها را می‌سازد و `src/main.tsx` آن را به React وصل می‌کند.

Context فقط نمونه store را به درخت می‌دهد.

## الگوریتم

جستجوی کامل با هرس فاصله. نوبت بدون ظرفیت یا خارج از بازه حذف می‌شود. ترکیب‌ها به ترتیب خدمات ساخته می‌شوند و اگر فاصله دو نوبت متوالی از حداقل کمتر باشد همان شاخه قطع می‌شود. حداقل فاصله در یک مرکز ۱۰ دقیقه و بین دو مرکز ۳۰ دقیقه است؛ برابری با مرز مجاز است. از بین برنامه‌های معتبر فقط سه تای بهتر نگه داشته می‌شود: پایان زودتر، سپس مجموع فاصله کمتر، سپس مقایسه ASCII شناسه نوبت‌ها. مجموع فاصله فقط فاصله بین نوبت‌های متوالی است.

اگر `k` تعداد خدمت (۲ یا ۳) و `n` نوبت هر خدمت بعد از فیلتر باشد، زمان `O(n^k)` است. حافظه نتیجه‌ها ثابت است چون بافر سه عضوی است. سقف ارزیابی `50^3 = 125000` ترکیب است.

هیوریستیک «زودترین نوبت» بهینه نیست؛ نوبت زودتر در خدمت میانی می‌تواند پایان کل برنامه را دیرتر کند. در این سقف جستجوی کامل هم دقیق است هم به‌اندازه کافی ارزان. روی این ماشین، در چند اجرای `npm test`، همین بدترین حالت حدود ۴۰ تا ۹۰ میلی‌ثانیه طول کشید. عدد هر اجرا با برچسب `[bench]` چاپ می‌شود. این از تأخیر ۳۰۰ms دریافت داده کمتر است، برای همین محاسبه بعد از رسیدن اسنپ‌شات روی همان نخ رابط اجرا می‌شود و Worker اضافه نشده. اگر `n` خیلی بزرگ‌تر از ۵۰ شود، قدم بعدی انتقال همین تابع خالص به Worker است، نه تقریب.

## وضعیت و ابزار

قواعد دامنه state ندارند. ظرفیت Mock در حافظه زیرساخت و فقط تا عمر صفحه می‌ماند. فرم، فاز، نتیجه‌ها و رسید در Zustand هستند تا دامنه به کتابخانه UI وابسته نشود. Redux برای یک صفحه فقط اقدام و reducer اضافه می‌کرد.

Vite کافی است چون صفحه یکی است و SEO لازم نیست. Tailwind برای UI است. Vitest کنار همان ابزار ساخت اجرا می‌شود. مسیریاب اضافه نشده.

## تصمیم‌ها

**جستجوی کامل، نه هیوریستیک.** هیوریستیک ارزان‌تر است ولی سه برنامه برتر را تضمین نمی‌کند. با سقف ۵۰ نوبت، هزینه جستجوی کامل از تأخیر Mock کمتر است. هرس فاصله همان قاعده دامنه است.

**Mock درون‌حافظه‌ای، نه MSW.** قرارداد این تمرین رفتاری است: تأخیر، کپی مستقل، ثبت همه‌یا‌هیچ و کد `SLOT_UNAVAILABLE`. status 409 فقط وقتی معنا دارد که آداپتر HTTP اضافه شود. پورت‌ها جایگزینی Mock با `fetch` را باز می‌گذارند.

**Zustand، نه Redux.** وضعیت فقط مال همین صفحه است. store وانیلی بدون رندر تست می‌شود. Context صرفاً همان store را تزریق می‌کند و مرز دامنه را تمیزتر نمی‌کرد اگر Redux بود.

## زمان و ادامه کار

پیاده‌سازی در یک نشست انجام شد و به بودجه حدود ۱۴ ساعت پیشنهادی نرسید. جریان اصلی ناقص نمانده.

اولویت ادامه:

1. آداپتر HTTP روی همین پورت‌ها، با تست قرارداد.
2. تست مرورگر برای سناریوی پاسخ خارج از ترتیب. تست کامپوننت مسیر انتخاب و ثبت موفق را می‌پوشاند.
3. انتقال محاسبه به Worker، فقط اگر سقف نوبت از ۵۰ بالاتر برود.

تقسیم بعدی: نفر اول مالک domain، application و تست قواعد می‌ماند. نفر دوم Mock و presentation. کار موازی بعد از تثبیت پورت‌ها و نوع `Schedule` شروع می‌شود.

دو ریسک: اگر شمارنده درخواست از use case خارج شود و در UI دوباره نوشته شود، پاسخ کهنه نتیجه را عوض می‌کند. اگر زیرساخت به‌جای کپی، ارجاع مشترک برگرداند، تغییر ظرفیت اسنپ‌شات قبلی را هم خراب می‌کند.
